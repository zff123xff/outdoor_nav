# patrol_node

Ping-pong patrol along the line segment between two GPS points.

The node exposes a ROS 2 action server (`patrol_node/action/Patrol`). The
goal carries the two GPS endpoints of the patrol line; the robot walks the
segment back and forth until the goal is canceled or `max_laps` round trips
are done.

The action interface and the node live in **one package**: `action/Patrol.action`
is defined here, so there is no separate `patrol_msgs` package to build.

## Data flow

```
patrol_node/action/Patrol  (goal: start_point, end_point)
        │
        ▼
patrol_node  ← this package
        │  ┌───────────────────────────┐
        │  │ waypoint queue + odom watch│
        │  └───────────────────────────┘
        │
        ├──> /gp_goal (sensor_msgs/NavSatFix, one waypoint at a time)
        │             │
        │             ▼
        │     nav2_input_bridge ── llaToEnu ──> /goal_pose
        │                                              │
        └──<── /odom (arrival feedback)                 ▼
                                                     straight_planner
                                                          → controller_server
```

## The ping-pong

The waypoint queue starts as `[A, B]`. Whenever a point is reached it is
pushed back onto the **tail** of the queue:

```
queue [A, B] → dispatch A → queue [B]
reach A      → push A     → queue [B, A] → dispatch B → queue [A]
reach B      → push B     → queue [A, B] → dispatch A → queue [B]   ...
```

The queue therefore always holds exactly one pending target and the
dispatched targets alternate `A, B, A, B ...`.

Arrival is detected from the odom position: the target counts as reached
after `consecutive_required` consecutive samples within `reach_threshold_m`
of the target's ENU projection — the same rule `multi_goal_to_gp_goal` uses,
and `lla_to_enu` is imported from that package so the ENU frame is exactly
the one `nav2_input_bridge` publishes the goal in.

## Action interface

`patrol_node/action/Patrol` — see `action/Patrol.action` for the
field-by-field docs.

| Group | Fields | Purpose |
|---|---|---|
| identity | `mission_id`, `agent_id`, `capability_id`, `primitive_id` | composing the primitive with others; echoed in the result and feedback |
| segment | `start_point`, `end_point` | the two GPS endpoints |
| transition | `current_pose` | the pose at handover, seeds the arrival check |
| transition | `hold_time_at_endpoint_s` | dwell at an endpoint so the next primitive can take over |
| transition | `max_laps` | stop after N round trips (`0` = run until canceled) |
| transition | `keep_moving_on_end` | keep the robot running when the primitive ends, instead of stopping it |
| result | `final_pose` | where the robot ended up, for the next primitive to pick up |

## Build

```bash
cd ~/outdoor_nav
colcon build --packages-select patrol_node
source install/setup.bash
```

## Run

```bash
ros2 launch patrol_node patrol_node.launch.py robot_namespace:=robot_a
```

`reference_latitude/longitude/altitude` are **auto-loaded from
`src/robot_launch/config/go2w_nav2.yaml`** (`nav2_input_bridge.ros__parameters`)
at launch time, so the arrival check always agrees with the nav2 stack.
Edit that one YAML when you move to a new test site.

For the wheeled-robot variant:

```bash
ros2 launch patrol_node patrol_node.launch.py \
    robot_namespace:=robot_a \
    nav2_params_yaml:=/home/nhy/outdoor_nav/src/robot_launch/config/gp_goal_nx_nav2.yaml
```

## Send a patrol

```bash
ros2 action send_goal /robot_a/patrol patrol_node/action/Patrol \
"{mission_id: m1, agent_id: uav1, capability_id: patrol_line,
  primitive_id: p1, max_laps: 0, hold_time_at_endpoint_s: 1.0,
  start_point: {latitude: 40.9445353, longitude: 113.172819, altitude: 1298.7345711},
  end_point:   {latitude: 40.9446353, longitude: 113.172819, altitude: 1298.7345711}}"
```

Cancel it with:

```bash
ros2 action cancel /robot_a/patrol
```

On cancel the node clears the waypoint queue and publishes `stop_planner`
once, which makes `straight_planner` cancel the active `FollowPath` and stop
the robot. Set `keep_moving_on_end: true` in the goal to skip that and let
the next primitive take over from `final_pose`.

## Caveats

- `patrol_node` and `multi_goal_to_gp_goal` both publish to `/gp_goal`.
  Do not run a waypoint mission while a patrol is active — the two would
  fight over the robot's goal.
- `straight_planner` remembers the position it was stopped at and rejects new
  goals within 0.1 m of it. Restarting a patrol whose first target is that
  close to the stop point would be rejected; normally the first target is a
  whole segment away, so this does not bite.

## Package layout

```
patrol_node/
├── action/Patrol.action     # the action interface (generated by rosidl)
├── patrol_node/             # the python module
│   ├── patrol_node.py       #   the node itself
│   └── waypoints.py         #   GeoPoint + PingPongQueue (no ROS imports)
├── scripts/patrol_node      # console entry point (ros2 run patrol_node patrol_node)
├── config/ launch/ resource/ test/
├── CMakeLists.txt           # ament_cmake: interfaces + python module
└── package.xml
```

The python module is installed into the same namespace as the generated
action (`site-packages/patrol_node/`), so the node imports the action as
`from patrol_node.action import Patrol`.

`waypoints.py` holds the queue logic without any ROS import, so it can be
unit tested straight from the source tree.

## Tests

Run them from the package directory — the lint tests check the package tree
relative to the current working directory:

```bash
cd src/external_pkg/patrol_node
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest test/
```

(`PYTEST_DISABLE_PLUGIN_AUTOLOAD=1` sidesteps a pre-existing env clash
between pytest and ROS's `launch_testing` plugin.)

Or through colcon, which runs the unit test:

```bash
cd ~/outdoor_nav
colcon build --packages-select patrol_node --cmake-args -DBUILD_TESTING=ON
colcon test --packages-select patrol_node
```
